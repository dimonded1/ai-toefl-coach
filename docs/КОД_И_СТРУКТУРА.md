# AI TOEFL Coach: краткий обзор кода и структуры

Дата: 2026-06-09

## 1. Назначение проекта

AI TOEFL Coach, это одностраничное учебное приложение для подготовки к TOEFL iBT. Пользователь задаёт цель, проходит упражнения, получает прогноз балла, видит слабые зоны, копит историю ошибок и может запросить AI-план обучения через backend-прокси.

Ключевое допущение: проект сейчас ближе к продуктовой панели обучения, чем к лендингу. Поэтому дизайн должен служить ежедневной учебной задаче: быстро показать текущий статус, следующий шаг и причину рекомендации.

## 3. Как связаны части проекта

### Frontend

- `frontend/index.html` содержит всю разметку: sidebar, dashboard, goal setup, practice-секции, mini test, AI study plan, analytics.
- `frontend/src/styles/main.css` содержит тему, layout, карточки, кнопки, адаптивность и визуальные состояния.
- `frontend/src/scripts/data.js` хранит локальную TOEFL-базу: reference data, вопросы, skill metadata, названия секций.
- `frontend/src/scripts/profile.js` отвечает за профиль, localStorage, прогноз score, progress, mistakes, XP, streak, achievements, local study plan.
- `frontend/src/scripts/aiPlan.js` собирает профиль, вызывает Groq-backed backend API, рендерит score-gap visual.
- `frontend/src/scripts/calendar.js` рендерит календарь подготовки, countdown до экзамена и 8-недельный roadmap.
- `frontend/src/scripts/app.js` управляет навигацией, dashboard, практикой, mini test, аналитикой, toast и UI-событиями.

Порядок подключения скриптов важен: `data.js` → `scoring.js` → `analyticsModel.js` → `profile.js` → `aiPlan.js` → `calendar.js` → `app.js`. Сейчас код работает через глобальные функции и константы, без ES-модулей и сборщика.

Важно: `frontend/src` в текущей архитектуре является публичной статической папкой, а не закрытой source-папкой сборщика. В неё нельзя класть секреты, черновики или файлы, которые не должны раздаваться nginx.

### Backend

- `backend/server.js` поднимает Express, CORS, JSON body limit, базовые security headers, healthcheck и подключает основной роут `/api/ai`.
- `backend/routes/ai.js` ходит в Groq Chat Completions API, валидирует вход, ограничивает частоту запросов, ставит timeout и проверяет JSON-ответ модели.
- `backend/routes/gemini.js` оставлен только как legacy alias для старого `/api/gemini`.
- `docker-compose.yml` держит backend внутри Docker-сети через `expose`, frontend через nginx открыт на `8080`.
- `frontend/nginx.conf` проксирует `/api/` на текущий backend URL деплоя. Для временного Render-деплоя это `https://ai-toefl-backend.onrender.com`; для локального Docker Compose можно вернуть `http://backend:3001`.
- Для локального `npx serve` и `file://` frontend обращается к `http://localhost:3001/api/ai` напрямую, поэтому backend должен быть запущен отдельно.

## 4. Что уже структурировано

- Статические файлы фронта перенесены из плоских `frontend/css` и `frontend/js` в `frontend/src/styles` и `frontend/src/scripts`.
- `frontend/index.html` обновлён на новые пути.
- `README.md` обновлён под новую структуру.
- `frontend/nginx.conf` теперь отдаёт `/src/` с настоящим `404`, чтобы отсутствующий JS/CSS не маскировался HTML fallback-ом.
- Добавлен `frontend/.dockerignore`, чтобы nginx-образ не забирал локальные мусорные и env-файлы.
- Добавлен `PRODUCT.md`, чтобы зафиксировать продуктовый register, пользователей, цель, анти-референсы и принципы дизайна.

Логика приложения не переписывалась. Это намеренно: перенос структуры сделан без смены архитектурной модели, чтобы не сломать текущий vanilla JS.

## 5. Оценка frontend

### Сильные стороны

- Уже есть полноценный продуктовый набор: goal setup, dashboard, practice, mini test, AI plan, analytics, mistake bank, XP/streak.
- Dashboard собран вокруг правильных сущностей: target score, current prediction, score gap, days left, weak zones, daily plan.
- Тема централизована через CSS variables.
- Есть локальный fallback для AI-плана, поэтому приложение не полностью зависит от внешнего AI API.

### Слабые места

- Dashboard перегружен равнозначными карточками. Пользователь видит много блоков, но не видит один главный следующий шаг.
- Навигация слишком дробная: каждый skill вынесен в отдельный пункт sidebar, из-за этого продукт выглядит как набор демо-разделов.
- В UI много emoji. Они помогают быстро понять смысл, но снижают ощущение серьёзного учебного инструмента.
- Много inline styles внутри JS-рендеринга. Это мешает довести интерфейс до системного состояния.
- Не хватает явных focus states, ARIA-состояний, live region для toast, confidence у TOEFL prediction.

## 6. Оценка backend, AI и расчётов

### Сильные стороны

- Backend изолирует API key от браузера.
- Есть healthcheck, ограничение размера JSON тела, security headers, rate limit, request timeout и базовая validation схема.
- AI prompt builders разделены по сценариям: study plan, score gap, feedback.
- Ответ AI запрашивается и проверяется в JSON-формате, а frontend умеет fallback на локальный план.

### Слабые места

- Нет полноценной auth/session модели на AI-прокси. В Docker backend закрыт от прямой публикации, но для публичного SaaS потребуется пользовательская авторизация и квоты.
- Нет базы данных: весь прогресс хранится в localStorage. Это нормально для прототипа, но не для кросс-девайс обучения.
- Скоринг уже учитывает сложность, свежесть и confidence, но всё ещё живёт только на клиенте.
- В reference data упомянута новая шкала TOEFL `1-6`, но UI и расчёты продолжают жить в `0-120` и `0-30`. Нужен явный conversion layer или выбор одной продуктовой шкалы.
- Scoring model версионируется, но prompt contract ещё стоит вынести в отдельный документ/тест.

## 7. Оценка дизайна

### Удобство

Базовая навигация понятна, но экранов и карточек слишком много для ежедневного сценария. Основной вопрос пользователя: "что делать сейчас, чтобы приблизиться к цели?" Сейчас ответ размазан между Today's Study Plan, Weak Zones, Smart Focus, Quick Practice и AI Study Plan.

### Красота

Интерфейс аккуратный, но generic: тёмный slate/blue/purple dashboard, одинаковые карточки, стандартные bars. Для TOEFL-продукта лучше двигаться к более академичной, спокойной и уверенной эстетике.

### Простота

Функций много, но они не объединены в один learning loop. Нужно укрупнить сценарии: Dashboard, Practice, Mistakes, Study Plan, Analytics, Profile.

### Неперегруженность

Главная проблема: почти все карточки имеют одинаковый визуальный вес. Нужны уровни важности:
- главный блок действия;
- диагностические метрики;
- доказательства и история;
- вторичные быстрые переходы.

## 8. План улучшений

### Этап 1. Безопасная техническая уборка

1. Дальше разделить backend на `routes`, `services`, `prompts`, `validators`, `config`.
2. Добавить user/session auth для AI API перед публичным деплоем.
3. Разделить frontend JS на доменные файлы: navigation, dashboard, practice, mini-test, analytics, ai-plan, storage/scoring.
4. Убрать inline styles из JS в CSS-классы.
5. Добавить smoke-тесты для статических путей и healthcheck.

### Этап 2. Улучшение dashboard

1. Собрать первый экран в три зоны: Score cockpit, Today focus, Evidence.
2. Добавить главный CTA: например `Start 20-min focus session`.
3. Объединить Today's Study Plan и What to Improve Today.
4. Добавить confidence к TOEFL prediction: sample size, last updated, confidence level.
5. Перенести навыки из sidebar в Practice tabs.

### Этап 3. Улучшение расчётов

1. Ввести веса по difficulty: easy, medium, hard.
2. Учитывать свежесть попыток, а не только общий historical accuracy.
3. Разделить progress и proficiency: прогресс по объёму практики не должен смешиваться с оценкой навыка.
4. Добавить confidence score: низкий, средний, высокий, на основе количества задач и разнообразия типов.
5. Версионировать scoring model, чтобы изменения расчёта были прозрачными.

### Этап 4. AI-процессы

1. Переименовать API слой под реального провайдера или сделать provider-agnostic adapter.
2. Добавить schema validation для входа и выхода AI.
3. Добавить auth/session или хотя бы rate limit для защиты Groq key.
4. Добавить timeout и понятную ошибку, если AI недоступен.
5. Сохранять AI-рекомендации с причиной: какие ошибки, skill gaps и цели использованы.
6. Сделать AI feedback более связанным с TOEFL rubrics, а не только с общими критериями.
7. Разделить system/developer/user prompt roles и валидировать JSON-ответ на backend, а не regex-ом на клиенте.

### Этап 5. Данные и база

1. Оставить localStorage как offline mode.
2. Добавить backend-хранилище профиля, попыток, ошибок и AI-рекомендаций.
3. Минимальная модель данных: users, profiles, attempts, answers, mistake_bank, study_plans, ai_feedback.
4. Добавить экспорт/импорт прогресса, пока нет полноценной авторизации.

### Этап 6. Дизайн-система

1. Заменить emoji в навигации и кнопках на единый icon set.
2. Ввести уровни карточек: primary action, metric, insight, secondary list.
3. Добавить полноценные focus states и reduced-motion.
4. Пересобрать mobile: sticky primary action, compact score chips, collapse secondary sections.
5. Подготовить `DESIGN.md` с токенами цвета, типографики, spacing, components и state vocabulary.

## 10. Риски

- Переход на ES-модули без сборщика может сломать порядок глобальных зависимостей. Лучше делать отдельным этапом.
- Рефакторинг scoring logic изменит пользовательские прогнозы. Нужны regression fixtures.
- Подключение базы потребует миграции localStorage и решения по auth.
- Изменение дизайна dashboard без продуктовой логики может просто переставить перегрузку местами. Сначала нужен сценарий: цель → диагностика → действие → обратная связь.

## 11. Критерии готовности следующих изменений

- Приложение открывается через nginx и локальный static server.
- Все скрипты загружаются без 404.
- Прямые static URLs `/src/styles/main.css` и `/src/scripts/app.js` возвращают реальные файлы, а не HTML fallback.
- Dashboard показывает данные из localStorage/default profile.
- AI plan работает через `/api/...` или показывает local fallback.
- README и структура папок соответствуют фактическим путям.
- Для крупных изменений есть хотя бы smoke/regression checks.
